# 官服式预启动与托盘行为设计

## 目标

本批仅统一以下运行行为：

1. 打开登录器后，在账号登录前启动并预加载 `GameApp.exe`。
2. 登录成功后向已经存在的同一个 GameApp 进程注入认证结果，不重新启动进程。
3. 用户点击“开始游戏”后，只放行同一个 GameApp 进程进入游戏。
4. 标题栏减号保持普通任务栏最小化；关闭按钮默认隐藏到系统托盘。
5. 托盘左键恢复窗口，右键菜单提供“打开登录器”和“退出”。
6. 开始游戏后登录器隐藏到托盘；游戏启动失败时恢复登录器。

## 明确不做

- 不修改 `F:\QQ飞车\QQSpeed_Launcher`，该目录仅作为官服行为证据来源。
- 不修改数据库表、账号数据或 SQL。
- 不在本批实现自动更新。
- 不改动现有 GameApp 与 NativeBridge 的命令行/握手协议。

## 已核对的官服证据

- 官服日志在登录前已启动：
  `GameApp.exe -StartFromLauncher ... --preload-game`。
- 登录成功发生在预加载进程启动之后。
- 用户后续操作才放行游戏进入运行态。
- 官服减号是普通最小化；托盘具有恢复与退出入口。

## 当前项目差距

当前 `preloadGame()` 只读取安装身份、内嵌运行包并创建 utility process，未创建 GameApp。真正的桥接映射、Hook 载荷设置和 `beginSession()` 都发生在账号登录成功以后。

## 方案

### 1. 服务端预登录运行材料

客户端在独立短连接中发送 MsgID 3、`version = 2` 的预登录运行材料请求。服务端以 `subject = 0` 签发安装身份绑定的 v2 材料，不访问账号数据库。v2 使用 `QQSRMAT2` 并只允许当前发布包。旧客户端的 MsgID 1 登录成功后 MsgID 3、`version = 1`、`QQSRMAT1` 流程保持不变。

运行材料仅用于解包登录器内嵌的 NativeBridge/Hook，不代表账号认证成功。账号授权仍只由 MsgID 1 返回结果决定；v1/v2 解析器互相拒绝，不做隐式降级。

### 2. 客户端预加载

`start-session` 顺序调整为：

1. 验证安装身份并读取内嵌运行包；
2. 请求预登录运行材料；
3. 解包并内存映射 NativeBridge；
4. 设置 Hook 载荷；
5. 调用 `beginSession()` 创建 GameApp；
6. 等待桥接进入等待认证状态且取得有效 PID；
7. 才向界面报告“登录环境已准备”。

### 3. 登录与开始游戏

- 登录只请求账号认证，不再请求运行材料，也不再创建 GameApp。
- 登录成功调用 `applyAuth()`，等待桥接进入已认证状态。
- 密码错误属于可恢复失败：保留预加载 GameApp，同一 PID 可再次登录。
- 点击开始调用 `startGame()`，只释放桥接等待事件，不创建第二个 GameApp。

### 4. 托盘与退出

- 减号：`BrowserWindow.minimize()`。
- 关闭按钮：隐藏窗口，不终止预加载 GameApp。
- 托盘左键/“打开登录器”：显示并聚焦窗口。
- 托盘“退出”：进入明确退出流程，取消原生会话、清理映射和 GameApp，再退出 Electron。
- 应用真正退出时销毁 Tray，避免残留图标。

## 数据库与服务端同步结论

不需要数据库变更。需要同步发布一次服务端程序，因为服务端必须支持“未登录先取运行材料”。若只发新版登录器而服务器未同步，新登录器会在预加载阶段失败；旧登录器仍保持原有登录后取材料流程。

## 验收标准

1. 登录器打开、登录页出现前后可观察到 GameApp PID。
2. 登录前 PID、登录成功后 PID、点击开始后 PID 完全相同。
3. 错误密码后 GameApp PID 不变，可再次输入正确密码。
4. 减号进入任务栏；关闭按钮进入托盘；托盘可恢复和彻底退出。
5. 退出登录器后预加载 GameApp 与 utility process 均不残留。
6. 旧客户端的 MsgID 1 -> MsgID 3/v1 流程仍通过协议测试；新客户端首包仅为 MsgID 3/v2。
7. `F:\QQ飞车\QQSpeed_Launcher` 全目录哈希在实施前后不变。
