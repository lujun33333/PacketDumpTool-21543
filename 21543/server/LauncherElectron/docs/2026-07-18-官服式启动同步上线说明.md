# 官服式启动同步与上线说明

## 一、本次已经同步的行为

本轮只处理“先同步官服操作”的范围：

1. 打开登录器后，不等账号登录，立即准备并预加载 `GameApp.exe`。
2. 登录成功后把认证结果交给已经存在的 GameApp，不重新创建进程。
3. 点击“开始游戏”只放行同一个 GameApp；预加载、登录、开始三个阶段校验同一 PID。
4. 密码错误时保留预加载进程，可以直接重新输入密码。
5. 标题栏减号仍是普通任务栏最小化。
6. 标题栏关闭按钮改为隐藏到托盘，不结束预加载进程。
7. 托盘左键或“打开登录器”恢复窗口；“退出”才执行会话清理并退出。
8. 多个启动流程各自持有窗口隐藏状态，某一个失败不会错误恢复或永久隐藏窗口。

官服参考目录 `F:\QQ飞车\QQSpeed_Launcher` 全程只读。实施前后共 712 个文件，SHA-256 对比差异为 0。

## 二、数据库和服务端结论

### 数据库

**不需要改数据库，不需要执行 SQL，也没有数据库回滚步骤。**

账号登录仍使用原来的 MsgID 1 和原来的账号数据库路径。本次新增的是登录前独立短连接的 MsgID 3/v2 运行材料请求，它不查询账号表。

### 服务端

**必须先同步服务端，再发新版登录器。**

新服务端同时支持：

- 旧登录器：登录成功后请求 MsgID 3/v1；
- 新登录器：登录前请求 MsgID 3/v2，随后账号连接只发送 MsgID 1。

因此服务端先上线不会阻断旧客户；反过来，如果先发新版登录器而服务端仍是旧版，新登录器会在 GameApp 预加载阶段失败。

## 四、最稳妥的上线顺序

### 第 1 步：备份当前线上服务端

1. 记录当前服务端进程实际路径和文件名。
2. 停止当前服务端。
3. 备份原 EXE、启动脚本和配置文件。
4. 不改 `ASpeedConfig.yml`、数据库配置、端口或其他 DLL。

### 第 2 步：只更新服务端 EXE

1. 用上面与现网同名的新版 EXE 替换旧文件。
2. 启动服务端。
3. 确认登录地址 `43.226.61.100:29999` 正常监听，日志没有运行材料配置错误。
4. 先用旧登录器登录一次，确认 v1 兼容链路正常。

### 第 3 步：小范围验证新版登录器

先只给自己的测试电脑或一个测试客户安装，不要立即全量发送。

验收顺序：

1. 打开登录器，在输入账号前确认已出现 `GameApp.exe`。
2. 记录 GameApp PID。
3. 故意输入一次错误密码，确认 GameApp 没有退出、PID 没变。
4. 输入正确密码，确认 PID 仍不变。
5. 点击“开始游戏”，确认进入游戏且 PID 仍为原 PID。
6. 测试减号：窗口进入任务栏。
7. 测试关闭按钮：窗口消失但托盘图标存在。
8. 从托盘恢复窗口。
9. 从托盘选择“退出”，确认登录器、utility 和尚未放行的 GameApp 均不残留。

可用 PowerShell 观察 PID：

```powershell
Get-Process GameApp -ErrorAction SilentlyContinue |
  Select-Object Id, StartTime, Path
```

### 第 4 步：再发给客户

只有第 3 步完整通过后，才把客户端安装包发给客户。服务端保持新版，不要在客户已更新后单独回滚服务端。

## 五、回滚方法

### 只发布了服务端、还没发新客户端

可以停止服务，恢复备份的旧 EXE，再重新启动。数据库无需回滚。

### 已经把新客户端发给客户

不要只回滚服务端。新版客户端依赖 MsgID 3/v2；旧服务端不支持时，新客户端会拒绝继续打开游戏。

此时有两个选择：

1. 优先修复并保留新版服务端；
2. 服务端和客户登录器一起回滚到旧版。

## 七、本轮没有做的事项

1. 自动更新：尚未实现，当前仍需手工发送安装包。
2. 强制更新：尚未实现，当前没有“不更新就打不开”的版本门禁。
3. 内存专项优化：尚未做。同步官服的登录前预加载会让 GameApp 在登录页阶段就占用内存，这是功能本身的直接成本。
4. 匿名预加载材料只保护传输，不把安装公钥当作账号授权。若以后要求 Hook 内容必须在登录后才可取得，需要把“公开预加载部分”和“登录后敏感部分”拆成两层发布包。

自动更新建议作为下一批独立实现：版本清单签名、服务端最低版本门禁、差分/整包下载、SHA-256 校验、原子替换、失败回滚；不要和本轮官服式启动链路混在同一次上线中。
